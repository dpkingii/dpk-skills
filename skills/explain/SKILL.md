# Clear explanations

## 1. Pick the reader

Use the audience the user names. Otherwise infer it from context (a recruiter, a classmate, a senior engineer, the user) and say in one line who you wrote for. If the right answer depends heavily on the audience and you can't tell who it is, ask.

## 2. Get the facts right

If the subject is code in the current project, read the code before explaining it. Separate what you confirmed from what you inferred. When something is uncertain, say what is unknown and how to check it.

## 3. Structure it

1. Start with what the thing is and what problem it solves, in one or two sentences.
2. Explain how it works, with the steps in the order they happen. Name the component that does each step.
3. Give one concrete example with real values, from the codebase when possible.
4. Mention limits or gotchas only if they matter to this reader.

Match the length to the question. A short question gets a short answer.

## 4. Write the sentences

- One idea per sentence.
- Use common, concrete words. Keep a technical term when it is the correct one, and define it the first time.
- Expand each acronym the first time it appears.
- Use active voice and name who or what acts.
- State cause and effect directly.
- Use lists for steps or parallel items, and prose when the ideas depend on each other.
- Cut filler, vague intensifiers and decorative jargon.
- No em dashes or semicolons. Don't end with a summary that repeats what you just said.

Don't give up accuracy to make it shorter.

## 5. Rewriting the user's text

When the user hands you their own explanation, keep their wording and structure wherever they already work. Fix only what is unclear or wrong. After the rewrite, list the changes that matter in a few short lines.

## 6. Check before finishing

- Every pronoun has a clear referent.
- Every term is defined or already familiar to this reader.
- Each step says what changes and why.
- In a rewrite, no fact from the original was lost.
